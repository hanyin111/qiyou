# 便笺人工验证协议核对

核对日期：2026-10-16；客户端版本：0.1.4。

0.1.3 真人测试：验证码可以显示，原神后续请求报 10306，铁道报 -1；便笺读取尚未通过。之前的 Windows 极验公开示例检查只能证明 SDK 与消息通道可加载，不能证明账号验证成功。

核对依据为[米游社官方工具](https://webstatic.mihoyo.com/app/community-game-records/)发布的 [bundle_546fbd77404c448f92cc.js](https://webstatic.mihoyo.com/app/community-game-records/bundle_546fbd77404c448f92cc.js)；不把桌面下载引导页当作可用验证入口。仅据公开协议独立实现，没有将第三方插件代码嵌入 Flutter。

已确认并修正的差异：

- 获取与确认均附带 `x-rpc-challenge_game`、触发失败请求的完整地址（不含查询参数）`x-rpc-challenge_path`、该响应的 `x-trace-id` 对应的 `x-rpc-challenge_trace`。追踪标识仅在内存保留，按账号、设备、角色隔离。
- 获取验证码使用 `is_high=true`，DS2 签名覆盖实际查询参数。极验服务不可用时停止验证，不接受离线成功。
- 人工完成后，提交 SDK 的三个 `geetest_*` 字段；DS2 签名覆盖实际发送的 JSON 正文。
- 确认成功的 `data.challenge` 是后续查询用的新凭据，必须允许这一成功响应并读取它。0.1.3 错误地准备使用极验原始 challenge，而且会把确认响应的新 challenge 误判为又一次风控。
- 新凭据只用于下一次相同角色的便笺查询，至多保留五分钟，不写入账号存储。不将空响应当作验证完成。
- 获取、确认、查询失败分别显示阶段与官方错误码，不记录或显示 Cookie、验证码令牌、请求正文或原始响应。

真实账号能否通过仍由米游社服务端决定。0.1.4 必须继续由账号本人手动测试；没有自动解题、代打码或伪造验证结果。

## 0.1.5：设备会话

0.1.4 真人反馈：三个游戏的确认步骤仍报 10306，未解决。对照 GsCore 的请求初始化发现它会在请求前获取 `x-rpc-device_fp`；旧实现缺少这一步。

米游社公开网页的[社区初始化 SDK](https://webstatic.mihoyo.com/dora/biz/mihoyo-community-init/main.js)和网站脚本使用 WEB 平台及浏览器实际环境生成设备信息。Windows 原生匿名测试已确认能通过官方网页取得 `DEVICEFP`、`_MHYUUID` 和当前浏览器 User-Agent，没有访问用户账号存储。

0.1.5 在用户点击验证后完成这一步。官方初始化页面只接收已有的四个设备 Cookie，不提供账号认证 Cookie；验证码页面仍不包含认证数据。设备元数据随账号使用原有系统加密存储，先重试便笺，再决定是否需要人工验证码。服务端下发的 `aliyungf_tc`、`acw_tc` 在记录请求之间按账号、设备、域名隔离保留，最多十分钟，不能覆盖认证 Cookie。

以上是已确认缺项的修正，并非证明 10306 已完全解决。真实验证结果仍待账号本人测试；新增脱敏诊断便于继续区分具体原因。
